# Thirty-two linked worktrees — September 16

The isolated candidate passed a 32-worktree lifecycle qualification using one
4-CPU/6-GiB development VM. A synthetic repository had 32 actual Git linked worktrees
on separate branches, producing 32 distinct project namespaces. Each ran one small
read-only-root HTTP service with a 64 MiB memory limit, 0.1 CPU limit and its own
persistent named volume. No application secrets, global runtime or user worktree
was changed.

All 32 services started in sequence, returned unique persistent UUID tokens through
reservation-bound private bridges, and underwent ordinary compute cleanup. The
resulting inventory contained 32 retained volumes with zero container references.
The first and last worktrees then restored together, served their original tokens,
and remained healthy during the observation window. The other 30 stayed retained
without compute. Explicit removal returned guest storage inventory to its baseline,
including retained reusable image identity/count/bytes.

Median initial start-to-private-response time was 0.696 seconds across 32 starts.
The two wake-to-private-response checks took 0.767 and 0.708 seconds. These timings
include graph invocation, inspection, bridge reservation/start and token readback;
they exclude Git worktree creation, planning and image load. They are synthetic
component timings, not a Docker/Compose comparison or an application percentile.

## Resource observations

Each condition used one approximately ten-second quiet window. CPU is native CPU
time summed over the verified provider process tree, normalized to one CPU core.
Footprint is the sum reported for those processes; shared pages may overlap. These
observations do not include unrelated processes or claim whole-machine accounting.

| Condition | Provider-tree CPU, percent of one core | Provider-tree footprint, MiB |
| --- | ---: | ---: |
| Empty VM before workload cycle | 0.850 | 670.74 |
| 32 retained worktrees, no active compute | 0.782 | 947.60 |
| Two active, 30 retained | 2.170 | 947.85 |

The small difference between the empty and retained CPU samples is within the
limitations of this short, sequential observation; it is not evidence of a CPU
improvement. More importantly, stopping compute did not restore the starting memory
footprint: approximately 277 MiB remained above the empty sample. Guest page cache,
engine state and provider reclamation need separate attribution. No automatic idle
policy or memory-return claim follows from successful stop/restore.

## Remaining gates

This establishes 32 distinct linked-worktree graph instances with a bounded active
subset and data-preserving explicit stop/restore. It does not establish automatic
idle suspension, simultaneous admission/wake races, activity/keep-awake leases,
long-lived socket or transaction quiescence, credential renewal, missing-checkout
recovery, large application parity, or matched Docker/Compose resource wins.
Next investigate the retained working set and a lease-aware opt-in idle policy;
keep graceful stop, container freeze and actual memory/disk reclamation separate.
