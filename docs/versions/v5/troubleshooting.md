# Troubleshooting

Run `hack doctor` using the **same CLI, backend and home** as the command that
failed. On the Compose path, use the terminal from [Install](install.md). On
native, use the full `hack-next` path from [Try native](native/start.md).
Read the named finding before using `--fix`; some problems need a decision or
an original key, not an automatic repair. The Doctor summary aligns result
counts with their check groups and indents diagnostic details. The summary
uses the same layout with or without gum.

`hack doctor --json` returns `{ok:true,data:{schema:1,checks,summary,counts}}`. Each check adds an area, machine/project scope and a fix category (`safe`, `admin` or `manual`), argv after `hack`, and a documentation URL. Empty argv means consult the docs. The audit remains read-only; `ok:true` means the audit ran, while error findings still exit 1. Unknown checks offer no runnable repair.

For a targeted repair, `hack doctor --fix --only 'hack gitignore' --yes --json --path <repo>` repairs only Hack's managed ignore block, keeping user lines. It needs a Git checkout and leaves adopted, unsafe or read-only inputs alone. It rechecks the result and exits 1 when unconfirmed. `data.fix` reports `id`, `changed` and `confirmed`; no other check is run or repaired. Other IDs, absent consent and combinations with other repair modes refuse before writes. Broad `--fix --json` still refuses.

`hack doctor --fix --only 'polling watchers' --path <repo>` shows a diff that removes only the `CHOKIDAR_USEPOLLING: "true"` and `WATCHPACK_POLLING: "true"` lines old `hack init` generated, and writes nothing. Add `--yes` to apply it. It refuses an adopted project and any change that would alter more than those lines. With `--json`, `data.fix` adds `applied`, `removed` and `diff`. Plain `--fix` never runs it.

Use `hack doctor --machine --json` for a machine-only audit. It returns the same `checks`, `summary` and `counts` in the envelope, tagged `data.schema: "hack.doctor.machine.v1"` (listed in the machine-readable output reference); plain `hack doctor --json` keeps `schema: 1`. It skips project discovery and project checks even from a broken project checkout, and inspects only global stores for secrets hygiene. It also omits the retained gateway checks, whose resolver reads registered project configurations. Every finding has machine scope; failed or unavailable observations remain warnings/errors. It runs bounded read-only probes, including `runtime status --json` from the native executor for the native backend, never starts Docker, hackd or a native runtime, and accepts no project selection, browser observation or repair flags. The selected backend and home still come from the same environment as ordinary Doctor.
Use `hack doctor --disk` to report allocated and logical file bytes for the selected native home without starting its pool. Add `--json` for the Doctor report envelope. An incomplete scan is marked as a warning and its totals cover only the files observed. Run this as a standalone audit. Repair flags such as `--fix` cannot be combined with it. See [Local disk footprint](https://github.com/hack-dance/hack/blob/next/docs/reference/disk-footprint.md).

Each finding names the service, file and line. Doctor only reports platform pins and images; it can remove generated polling lines with the selected repair above. |
| `env override coverage`: “has no entry for running service …” (Compose) | An older Hack rewrote `.hack/.internal/compose.env.override.yml` for the services one targeted command named (`hack restart api`, `up api`, `run`, `exec`). A later Compose command can then recreate another service without its managed variables (HACK-2325). | Run `hack up` once in that checkout; current Hack writes the file for every service. The check expects an entry only for a running Compose service whose effective env for the default selection is non-empty (host lifecycle processes and services that remove every key with `null` need none), and it reads key names only, never values. It judges by the selection each running instance recorded, so a one-off `hack run --env <other>` or `exec --env <other>`, which rewrites the file without recording, can make it warn; run `hack up` with the instance's own `--env` to settle it. |

The pool belongs to the native home, so the check runs once per doctor run, in project runs too, marked as a machine check. | Run the stop command the message prints (`<native executor> --candidate-root <native home> runtime down --json`). The check warns only when `runtime status --json` reports `pool_idle: true`: running with a live provider and no graph (Compose or native-authored, running or retained), environment allocation or exec session. A stopped pool is OK. Unavailable runtime status or an unknown pool state instead warns that idleness could not be checked, with `nativePool.state: "unknown"`; this does not claim the pool is idle or suggest stopping it. `runtime down` refuses while an image build runs. Doctor never stops the pool, and `--fix` does not either. |
| `global install`, `global up` or `doctor --fix`: “The proxy cannot publish ports 80 and 443 … already in use by” or “The proxy could not start on ports 80 and 443 …” (since next.21, #913) | Another program already listens on port 80 or 443 on some address, for example a VPN client's serve feature. The command exits non-zero; install stops before DNS and trust setup. | Stop that listener, or publish the proxy on one address: `hack config set --global proxy.bind_address 127.0.0.1 && hack global install`. Install rewrites Hack's proxy compose file without a prompt, also without a terminal, and keeps a copy that differs from Hack's current rendering as `.bak-<UTC time>`. See [global settings](https://github.com/hack-dance/hack/blob/next/docs/guides/global-settings.md). |
| `proxy ports`: “port 443 on loopback is not reaching the Hack proxy” (since next.17, #773) | A hostname resolves to loopback, but its published port does not reach Hack's proxy. Another listener, a VPN's serve feature or the container runtime's HTTPS setting may own the port. Doctor checks only where the proxy's schemas name resolves on this machine, so a name that resolves straight to the proxy container is not warned about. | Review visible listeners, `proxy.bind_address` and local DNS overrides. Change the conflicting setting deliberately, then rerun Doctor. Port 80 working does not prove 443 works. Doctor applies no automatic fix. [Routing details](guides/proxy-network-repair.md). |
| `secret integrity`: encrypted store has entries, but its key is missing or does not open it (since next.17, #779) | An old global store remains, but the original key is unavailable. It is an error where the project reads it and a warning elsewhere. | Choose **restore the original key** or **retire the store** if the key is gone for good. Never create a replacement key to open old ciphertext. Retirement keeps the encrypted file and prints how to put it back. See the steps below. |
| `secret integrity`: env layer “could not be read or parsed” (since next.17, #766) | The layer is unreadable, invalid, or outside an allowed path. | Fix its access, syntax or location, then rerun Doctor. Keep the file and original key. If encrypted entries cannot be opened, recover that key; a hidden value in `env list` is not proof of decryption. [Env and keys](../env.md#secret-key-handling). |
| `daemon start`: “Started hackd process but it did not report ready yet”, or “hackd exited before it was ready (exit code N)” | With no service manager (containers, CI runners, cloud sandboxes, prerelease runs), `daemon start` starts hackd itself and waits up to 20 seconds for it to be ready, returning as soon as it is. “Not ready yet” means hackd was still running but not ready after that time. “Exited” means the process it started ended first; that is reported at once. Releases through `5.0.0-next.22` waited only 2 seconds, so a slow or busy machine could report a healthy hackd as not ready. | Run `hack daemon status`: if it is running and compatible, hackd finished starting and nothing more is needed. Otherwise read `hack daemon logs --tail 200`, or run `hack daemon start --foreground` to see the error. |
| `global install` or `global up`: “… started, but these containers are not running: hack-dev-proxy-coredns-1 (exited, exit code 1) …”; or on `5.0.0-next.23` and earlier, `up` warns “CoreDNS is not reachable” after a `global install` that said “Global infra is up” | A global container started and then stopped. On Linux the usual cause is a config it cannot read: `docker logs` for it shows `permission denied`. CoreDNS, Loki and Grafana do not run as root, so the configs they read under `~/.hack` must be readable by others. Through `hack-next`, releases up to `5.0.0-next.23` wrote them owner-only (the manager's private umask reached the CLI); a strict umask in your own shell (077) did the same. Later releases restore your umask for the CLI and set those few files to 0644 (and the Grafana dashboards directory to 0755) whatever the umask, but only while they still hold Hack's own content: a config you customised keeps the permissions you gave it, and the message names it with the `chmod` to run if you want the container to read it. | Upgrade, then run `hack global install` again: it resets those modes even when no file changed. For a customised config, run the `chmod` the message prints, or leave it private and expect that container to stay down. Without upgrading, run `chmod 644 ~/.hack/caddy/Corefile ~/.hack/logging/loki.yaml ~/.hack/logging/grafana/provisioning/*/*.yaml ~/.hack/logging/grafana/dashboards/*.json && chmod 755 ~/.hack/logging/grafana/dashboards`, then `hack global up`. For any other cause, read `docker logs --tail 50 <container>`. |
| `global install` or `global up`: `E_GLOBAL_NOT_READY` “… started, but this container was not ready within N s: …” or “… this container is unhealthy: …” | A global container is running but its healthcheck did not pass (Caddy's admin API, Loki's `/ready`, Grafana's `/api/health`, Alloy's `/-/ready`). `hack global up` waits for these instead of a fixed time, up to 30 s for the proxy and 120 s for the logging stack. | Run the `docker inspect` and `docker logs` commands the message prints. On a first start Grafana migrates its database; on a slow disk rerun `hack global up`. |
| `global install` or `global up`: `E_GLOBAL_NOT_READY` “The global proxy's containers are running, but within 15 s CoreDNS answered …, not only the proxy's address”, “… did not resolve the name”, “port 443 on … refused the connection” or “… answered with a certificate this home's proxy did not issue” | `hack global up` waits until routing works end to end: a `.hack` name resolved by CoreDNS (asked from inside the Caddy container) to the Caddy container's own address, and an HTTPS request for that name sent where this machine resolves it (the OS resolver; the proxy's live loopback bindings only when the machine has no answer yet), answered on a connection verified against the running proxy's CA. A wrong DNS answer or another server answering on 443 fails here. | Run the `docker logs` commands the message prints, then `hack doctor`. A firewall, a DNS override or another program on port 443 of the bind address shows up here. |

| `doctor`: “the global stack files predate readiness checks” | The global compose files were written by an older `hack global install`, so they have no healthchecks and `hack global up` keeps its old fixed waits (2 s for the proxy, 10 s for logging). | Run `hack global install` to rewrite them. |
| `hack global up`: `E_GLOBAL_NOT_READY` or `E_GLOBAL_STOPPED` | A global proxy or logging container did not become healthy within its bound, stopped right after starting, or DNS (CoreDNS) or HTTPS (port 443) through the proxy refused or answered wrongly at the end of the 15 s probe. `hack global up --json` returns the code in its error envelope, with `error.detail` in the `hack.global-up.v1` shape (`failedStage`, `logging`, `routes`). | Read the named container's `docker logs --tail 50`, then `hack doctor`. |
| `hack global up`: “Not checked: …” and success | The route probe could not check a step: this machine has no address for the schemas name yet (Hack's DNS is not set up, so HTTPS was tried only at the proxy's published loopback, where a refusal is not counted); the proxy image has no `nslookup` (a v4 proxy file); the Caddy container's address or the running proxy's CA could not be read; TLS on loopback 443 did not complete (a timeout or a reset: some container runtimes do not forward it; doctor reports this path); the proxy does not publish 443 on a loopback address; or the Docker engine is remote (SSH, TCP given by host name, or TCP with the proxy on one address). Plain `hack logs`, with or without `--since`/`--until`, keeps reading container logs without it. |

| `env-key-weak-permissions` | An old project key has group or other access. | Keep a private backup, then apply the reported `chmod 600` remedy to the named key. Do not move it to an unignored `.old` file in the checkout. next.16 has this check; newer builds also have the hygiene report below. |

| `local ca trust`: not trusted, or "could not tell" (since next.17, HACK-2218) | The system trust store (macOS System keychain; Linux system bundle and browser NSS databases) does not trust the current Caddy Local CA, or Hack could not read a store. | Run `hack global trust`, then rerun Doctor. | Native `up` (`registry_image`): “Registry layer download from <host> failed after N attempt(s): …” (since next.22, HACK-2330) | A layer body failed while it streamed from the registry, often under heavy host or network load. Each layer downloads to a private temporary file next to the image archive, is checked against its digest and size, and is retried up to 3 times within what remains of the image's 360-second deadline, which is never extended. The reason is the last attempt's: the transfer timed out, the connection ended before the whole layer arrived, the layer did not match its digest or size, the registry answered an HTTP error status, or the deadline was reached. `--json` carries the same sentence; the runtime's `network_request` diagnostic has `version: 2`, `host`, `attempts`, `reason` and, for an HTTP status, `status`, never a URL, query or credential. | Retry `up` once the host is less loaded; temporary layer files are removed on every path, and a completed layer is fetched again. A digest or size mismatch that repeats means the registry or a proxy between serves different bytes for that digest: check the named host rather than retrying. Access refusals (401, 403, 404) keep their own message about credentials or a missing image. |
| Native `up --detach` or `up --json` used to report only `E_STARTUP_INCOMPLETE`: “Native detached startup was not confirmed” when something failed before the VM started (merged after next.22, HACK-2339) | A detached native start runs in a background owner with no terminal, and only runtime failures reached the command that started it. | Current builds report a failure before VM work exactly as foreground `up` does, in text and `--json`: a failed `up.before` hook gives `E_LIFECYCLE_FAILED` (“Lifecycle (native up before) failed (exit N); values omitted.”), and, when stderr is a terminal, the hook's step line, the last 40 lines of its output and its failure line are written to stderr (never into the `--json` envelope). A captured stderr, such as an agent tool's result, gets the refusal and any retry guidance without the hook output, because that output may contain values: run `hack up` without `-d` in a terminal to see the hook's output; a source-size refusal gives `E_NATIVE_PROJECT_UNSUPPORTED` with its largest paths; settings and other closed refusals keep their own code and message. Compose prints a lifecycle blocker with the hook phase and exit code. Its JSON keeps `E_LIFECYCLE_FAILED` with “Lifecycle (up before) failed (exit N)”. Compose exits with the hook's status; native exits 1. A failure after VM work starts still reports `E_STARTUP_INCOMPLETE` with the runtime's detail; inspect `hack ps` before retrying. |

If native shutdown was interrupted during guest relay removal, repeat the same
shutdown or recovery command. An empty relay allocation can be removed on retry
when its recorded slot generation is stopped or discarded and its socket is gone.

When recovery archives a previous-boot shared HTTPS owner, it checks the frontend
invocation for this Hack home. Other users' processes and different executables
do not need readable arguments. If a possible owner still has unreadable
arguments, recovery keeps the retained state and reports `stop_uncertain`.

## A store whose key is lost

Use next.17 or later; earlier prereleases do not have `retire-store`. Doctor's
finding names the selected store and registered projects that read it.

1. Prefer restoring the **same original key** from a private backup or another
   machine, at the path Doctor names with mode 600.
2. If the key is gone for good, select the diagnosed project and retire the store:

   ```sh
   hack secrets retire-store --path /absolute/project --allow-unchecked
   ```

   On the Compose path, `hack` must be the Compose-selected v5 CLI, as on page 1.
   Pass `--allow-unchecked` only after confirming no shell for a project selecting
   the store holds its key in `HACK_SECRETS_FILE_KEY`; Hack cannot inspect another
   shell. The flag also acknowledges registered projects it could not check.
   A store a configured key still opens is refused. Without a terminal, `--yes`
   is also needed to confirm the move.

Retirement moves the file to a timestamped directory beside it. It deletes no
entries, leaves the key file alone and prints the restore command. It does not
recover the values. Keep the moved file if you might recover the key later.
[Store details](https://github.com/hack-dance/hack/blob/91c311e4d9540ea3ca32113a61458a26db90c704/docs/env.md#compatibility-notes)
cover the refusal and recovery rules.

If a report needs help, share the version, finding name and the action that failed.
Remove secret values and private paths from logs before sharing them.
